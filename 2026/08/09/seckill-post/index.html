基于 Spring Boot 的高并发秒杀系统：设计与落地

前言

这是我的毕业设计项目系列博客的第二篇。第一篇讲了为什么选这个题目，这一篇讲怎么落地。

作为一个报考**计算机技术（专硕）**的考生，我做这个项目的目标很明确：不止是为了通过答辩，更要让它成为复试时导师眼中的”硬通货”。

所以这篇文章不会只贴代码，我会重点讲每一个技术决策背后的思考——包括我踩过的坑、翻过的车、以及最终的解决方案。

一、为什么需要”三层防护”？

先想一个经典问题：100 件商品，1000 人同时抢。如果只靠一条 SQL 会怎样？

答案是：超卖 + 数据库被打死。

问题 原因
超卖 1000 个请求同时读到 stock > 0，都通过校验，库存扣到 -900
数据库连接池耗尽 1000 个并发同步写库，连接池（通常只有 20-50）瞬间占满，后续请求全部超时

解决思路：分层拦截

核心思想：让请求在到达数据库之前，就被层层过滤掉 99%。

每一层只做一件事，职责清晰，论文里画这张图非常加分。

2.2 异常与降级策略

环节 异常场景 处理方式
RateLimiter 限流 无法获取令牌 返回”当前抢购人数过多，请稍后重试”
Redis 防重 同一用户 5 秒内重复请求 返回”操作过于频繁”
Lua 预扣 库存不足（stock <= 0） 直接返回”已售罄”，不发 MQ
MQ 宕机 消息发送失败 回滚 Redis 库存（INCR），返回”系统繁忙”
Consumer 异常 消费者处理失败 回滚 Redis 库存 + 已购标记，结果写 FAIL
DB 库存不足 Redis 与 DB 数据不一致 事务回滚 + 库存回滚，结果写 FAIL

三、关键代码实现

3.1 Lua 原子脚本（防超卖的核心）

为什么不用 GET + DECR？

很多初学者会写成这样：

问题： get 和 decr 是两个独立操作，中间有时间窗口。当 100 个请求同时读到 stock = 1，它们都会通过 if 判断，然后各自执行 decr，最终库存变成 -99。

✅ 正确方案：Lua 脚本

Redis 执行 Lua 脚本时是单线程原子性的——脚本执行期间，不会有其他任何命令插入。所以”判断 + 扣减 + 记录”三步在 Redis 眼里是一步操作。

返回值约定：

返回值 含义 后续动作
-1 重复下单 返回”您已参与过本次秒杀”
0 已售罄 返回”手慢了，商品已抢完”
1 预扣成功 发送 MQ 消息，返回”排队中”

💡 复试考点： 导师可能会问”为什么用 Lua 不用 Java 代码控制？” 答案就是：Redis 的单线程模型 + Lua 的原子性保证。在 Redis 执行 Lua 期间，不会有其他客户端的命令插队，这是 Java 层面的锁无法做到的（因为 Java 是分布式的，多个实例之间锁不互通）。

3.2 Redis 防重 + Guava 限流

这两者是入口处的第一道和第二道闸门，顺序很重要：

为什么顺序是 限流 → 防重 → 预扣？

顺序 理由
限流第一 全局流量控制，挡掉绝大部分无效请求，减轻 Redis 压力
防重第二 在限流通过后，针对单个用户去重，避免同一用户狂点刷接口
预扣第三 最后才做库存判定，因为前两步已经过滤了 90% 的请求

3.3 MQ 异步消费（削峰填谷）

预扣成功后，立即返回”排队中”，订单通过 RabbitMQ 异步创建。这是提升 QPS 的关键一步。

为什么要异步？

假设同步下单需要 50ms（查库存 + 写订单 + 扣库存），那么 1000 并发 = 每秒需要处理 1000 个 50ms 的操作 → 数据库连接池瞬间爆炸。

异步化之后：Controller 只做 5ms 的 Redis 操作就返回，真正的下单由后台消费者慢慢消化（比如每秒处理 200 个），数据库压力骤降。

消费者（Service 层）

Mapper 中的乐观锁 SQL

关键点： WHERE stock_count > 0 这个条件就是数据库的乐观锁。即使 Redis 预扣通过了，如果 DB 层面库存已经为 0，这条 SQL 的 affected rows 就是 0，订单不会创建。这是最后一道防线。

五、QPS 性能对比

我用 JMeter 分别测试了三种方案在 1000 并发下的表现：

方案 并发数 平均 QPS 响应时间（avg） 超卖情况 系统状态
纯 DB（无优化） 1000 ~120 8500ms ❌ 有超卖 连接池溢出，大量超时
+ Redis 缓存 1000 ~850 120ms ✅ 无超卖 稳定
+ Redis + MQ 5000 ~3200 35ms ✅ 零超卖 非常稳定

结论： 引入 Redis + MQ 后，QPS 提升了 26 倍，响应时间从 8.5 秒降到 35 毫秒。

六、踩坑实录

6.1 Redis 与数据库数据不一致

现象： 偶尔出现 Redis 库存为 0，但数据库里还有剩余库存的情况。

排查过程：

  1. 查看日志，发现是 MQ 消费者在写入 DB 时抛了异常（数据库连接超时）
  2. 但此时 Redis 库存已经扣减了
  3. 导致”Redis 说没货了，DB 说还有货”的不一致状态

解决方案： 在 Consumer 的 catch 块中回滚 Redis 库存：

同时采用 Cache Aside Pattern：DB 操作成功后，主动删除 Redis 缓存，下次请求重新从 DB 加载。

6.2 重复下单的幽灵

现象： JMeter 压测时，极少数情况下同一个用户出现了两笔订单。

原因： 用户在 5 秒防重窗口过期后，再次发起了请求。

解决方案： 双重防护——

  1. Redis SETNX（5 秒窗口）：挡掉 99% 的重复请求
  2. DB 唯一索引：在 t_seckill_order 表上加 UNIQUE KEY uk_user_goods (user_id, goods_id)，即使前面的防线失效，数据库也会拒绝重复插入

6.3 Redisson 锁的坑

现象： 消费者处理时间超过 10 秒时，锁自动过期，导致另一个消费者拿到锁，出现并发问题。

八、总结

回顾整个项目，我从中学到的不仅是技术本身，更是架构思维：

  1. 不要相信任何一层防御是完美的。 即使 Redis 预扣成功了，DB 层面依然要做乐观锁兜底。多层防护不是冗余，是必要的安全网。

  2. 异步化是提升性能的银弹。 把”快速响应”和”实际处理”解耦，系统的吞吐量立刻提升一个数量级。

  3. 数据一致性是分布式系统永恒的主题。 缓存和数据库之间的同步、MQ 消息的可靠投递、消费者的事务回滚——每一个环节都可能出问题，必须有完善的补偿机制。

  4. 压测数据不会骗人。 优化前和优化后的 QPS 对比，是最有说服力的证据。不管是写论文还是面试，数字比文字更有力量。
