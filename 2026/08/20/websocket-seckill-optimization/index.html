前端秒杀排队体验优化：从轮询到 WebSocket 的升级之路

前言

在毕设项目《高并发秒杀系统》的开发过程中，下单结果的反馈机制一直是个痛点。随着功能的迭代，我意识到传统的 HTTP 轮询方案不仅浪费资源，而且用户体验极差。本文将记录我是如何将下单通知从”轮询拉取”优化为”WebSocket 推送”的，包括核心代码实现、降级方案设计以及遇到的问题排查。

1.3 暴露的问题

在 JMeter 压测 5000 并发用户时，这个方案暴露了两个致命问题：

问题一：服务器资源严重浪费

场景 并发用户数 轮询频率 每秒额外请求量 数据库查询量/秒
秒杀高峰 5000 1次/秒 5000 req/s 5000 次/秒
秒杀高峰 5000 2次/秒 10000 req/s 10000 次/秒

即使 80% 的请求在 Redis 预扣库存阶段就被拦截了，剩下 20% 真正进入队列的用户，依然会持续产生每秒上千次的轮询请求。这些请求大部分返回的都是”还在排队”，纯粹是无效查询。

问题二：用户体验割裂

从用户视角来看，点击按钮后看到的是一个无限转圈的 Loading 动画，不知道自己排在第几位，不知道还要等多久，甚至不确定请求是否丢失。这种”不确定性”带来的焦虑感，是用户体验的大忌。

1.4 方案选型

方案 实时性 服务器压力 兼容性 实现复杂度
HTTP 短轮询（旧） 差（1秒延迟） 高 极好 低
HTTP 长轮询 中 中 极好 中
WebSocket（新） 毫秒级 极低 好（需现代浏览器） 中
Server-Sent Events 好 低 较好 低

综合考虑实时性、资源消耗和项目技术栈（Spring Boot 原生支持 WebSocket），最终选择 WebSocket 方案。

2.2 优化后的完整流程

  1. 页面加载时建立连接：用户进入商品详情页，前端调用 connectWebSocket()，与后端建立长连接，URL 中携带 JWT Token 用于鉴权。
  2. 后端维护会话映射：@ServerEndpoint 在 onOpen 时将 userId → Session 存入 ConcurrentHashMap。
  3. 用户点击秒杀：前端发送 HTTP 请求到 /api/seckill，后端 Redis 预扣库存后，将消息推入 MQ，立即返回”已加入队列”。
  4. MQ 消费者处理订单：消费者从队列取出消息，执行下单逻辑（写数据库、扣库存），得到最终结果。
  5. 主动推送结果：消费者调用 WebSocketServer.sendMessage(userId, result)，后端从 Map 找到对应 Session，推送消息。
  6. 前端即时响应：前端 onmessage 回调触发，弹出”秒杀成功”或”秒杀失败”提示，无需任何轮询。

4. 遇到的问题与解决

4.1 问题一：WebSocket 鉴权

现象：WebSocket 握手阶段无法像 HTTP 请求那样自动携带 Authorization Header 或 Cookie。

分析：浏览器的 WebSocket API 不支持自定义 Header（部分浏览器支持 Sec-WebSocket-Protocol，但不够通用）。

解决方案：将 JWT Token 拼接在 URL Path 中，后端在 @OnOpen 方法中解析。

安全补充：生产环境建议使用 wss://（TLS 加密），防止 Token 在传输过程中被嗅探。

4.2 问题二：Nginx 反向代理导致连接失败

现象：本地开发环境一切正常，部署到服务器后 WebSocket 始终连接不上。

排查过程：

  1. 检查后端日志 → 没有收到任何连接请求
  2. 检查 Nginx 日志 → 发现 400 错误
  3. 查阅文档 → Nginx 默认将 WebSocket 当作普通 HTTP 请求处理，不会保持长连接

解决方案：在 Nginx 配置中增加 WebSocket 代理支持：

关键说明：Upgrade 和 Connection 这两个 Header 告诉 Nginx 这是一个协议升级请求（从 HTTP 升级到 WebSocket），需要保持长连接。

4.3 问题三：连接断开与自动重连

现象：手机端用户在 WiFi 和 4G 之间切换时，WebSocket 连接会断开，且不会自动恢复。

解决方案：实现三级重连机制 + 心跳保活。

4.4 问题四：多标签页重复连接

现象：用户打开多个标签页，每个标签页都建立一个 WebSocket 连接，导致后端 Map 中同一个 userId 被反复覆盖。

解决方案：后端在 onOpen 时检测已有连接，关闭旧连接。

4.5 问题五：MQ 推送时用户已离线

现象：用户秒杀后关闭了页面，MQ 消费者处理完订单后调用 sendMessage()，但用户已经不在线。

解决方案：增加离线消息暂存机制（可选进阶方案）。

6. 总结与展望

6.1 技术收获

通过这次优化，我深刻体会到以下几点：

  1. “推”比”拉”更高效：在数据实时性要求高的场景下，服务端主动推送天然优于客户端轮询。这不仅减少了无效请求，也降低了服务器负载。
  2. 降级策略是生产环境的必需品：任何”高级”技术方案都必须有对应的降级方案。WebSocket 虽好，但网络环境复杂多变，必须做好”降级为轮询”的兜底。
  3. 心跳机制不可忽视：长连接最大的敌人不是高并发，而是”假死连接”。30秒一次的心跳包，是保障连接可靠性的最低成本方案。
  4. Nginx 配置是部署的隐形坑：开发环境一切正常，上了服务器就报错——这种问题在微服务架构中极其常见，需要养成”本地通了不算通，线上通了才算通”的意识。

6.2 后续优化方向

方向 描述 预期效果
实时排队人数 利用 WebSocket 广播当前队列长度 用户看到”前方还有 128 人”，体验更佳
离线消息推送 用户断线后，消息暂存 Redis，重连后拉取 防止消息丢失
wss 加密传输 生产环境启用 TLS，防止 Token 泄露 安全性提升
集群化部署 多实例下使用 Redis Pub/Sub 同步 Session 支持水平扩展
WebSocket 连接池监控 接入 Prometheus + Grafana 监控在线人数 运维可视化

6.3 写在最后

技术的选型没有”最好”，只有”最合适”。WebSocket 不是银弹，但在秒杀通知这个具体场景中，它确实是最优解。这个项目让我明白：一个优秀的系统，不是由单一技术决定的，而是由”主方案 + 降级方案 + 监控方案”共同构成的。
